## Merge

Está permitido leer `"$VAR_S1_FILE"` únicamente para obtener variables necesarias de este paso.

Está permitido leer `"$ANALYSIS_FILE"` únicamente como fuente de verdad para el contenido funcional y técnico de este paso.

No está permitido usar ninguna otra fuente.

Objetivo:

Generar `MERGE_TITLE.txt` y `merge.txt` dentro de `"$OUTPUT_DIR"` usando exclusivamente `"$ANALYSIS_FILE"` como fuente de verdad para el contenido de cambios.

- `MERGE_TITLE.txt` debe contener únicamente la frase principal del merge
- `merge.txt` debe contener únicamente el cuerpo del merge

El contenido debe estar orientado a integración técnica de release. Su propósito es resumir de forma clara el alcance técnico más importante de la release y acompañarlo, si aplica, con viñetas breves de apoyo.

Las variables del flujo solo podrán utilizarse para metadatos estrictamente necesarios como ramas, versión y nombres de archivo. Queda prohibido inferir cambios desde otras fuentes.

### 6.1 Validar directorio de salida de merge

Leer `"$VAR_S1_FILE"` para obtener:

- `OUTPUT_DIR`
- `CURRENT_BRANCH`
- `TARGET_BRANCH`
- `RELEASE_VERSION`

Reglas:

- no inventar variables
- `OUTPUT_DIR` debe venir definido desde pasos anteriores
- si `TARGET_BRANCH` no existe, usar literalmente `develop`

Definir:

- `MERGE_TITLE_FILE="$OUTPUT_DIR/MERGE_TITLE.txt"`
- `MERGE_FILE="$OUTPUT_DIR/merge.txt"`

Acción:

`mkdir -p "$OUTPUT_DIR"`

Abortar si:

- `OUTPUT_DIR` no existe o está vacío
- `CURRENT_BRANCH` no existe o está vacío
- `RELEASE_VERSION` no existe o está vacío
- no puede crearse `"$OUTPUT_DIR"`

### 6.2 Leer análisis para merge

Leer `"$ANALYSIS_FILE"` y usarlo como única fuente de verdad para identificar exclusivamente:

- nuevas funcionalidades
- mejoras
- correcciones
- eliminaciones
- cambios de seguridad
- comandos nuevos o modificados enlazables en la documentación, si aparecen reflejados
- notas técnicas explícitas relevantes para la integración técnica de la release

Reglas:

- no usar `"$DIFF_FILE"`
- no usar archivos actuales del proyecto
- no usar historial de conversación
- no inferir cambios no escritos explícitamente en `"$ANALYSIS_FILE"`
- omitir categorías vacías
- no convertir dudas o ambigüedades en hechos
- centrar el contenido en el alcance técnico del merge
- no tratar este paso como documentación extensa ni como changelog completo

Abortar si:

- `"$ANALYSIS_FILE"` no existe
- `"$ANALYSIS_FILE"` está vacío
- `"$ANALYSIS_FILE"` no contiene información utilizable para redactar `MERGE_TITLE.txt` o `merge.txt`

---

### 6.3 Generar borrador de MERGE_TITLE.txt y merge.txt

Objetivo:

Crear el contenido textual del merge orientado a integración técnica de release, siguiendo un formato breve, claro y mantenible.

`MERGE_TITLE.txt` debe contener únicamente la frase principal del merge.

`merge.txt` debe explicar de forma breve qué integra la release y qué cambios clave acompañan esa integración.

Separación obligatoria de salida:

- `MERGE_TITLE.txt` debe contener una única línea con la frase principal del merge
- `merge.txt` debe contener únicamente el cuerpo del merge
- la frase principal no debe escribirse dentro de `merge.txt`
- el cuerpo no debe duplicar literalmente la frase principal
- si el merge se crea mediante un comando que separa título y cuerpo, cada fichero debe contener exclusivamente su parte correspondiente

Formato de salida requerido para `MERGE_TITLE.txt`:

```text
Frase técnica breve en inglés que represente el conjunto del merge
```

Formato de salida requerido para `merge.txt`:

```markdown
- cambio clave 1
- cambio clave 2
- cambio clave 3
```

#### Reglas para `MERGE_TITLE.txt`

- no usar prefijos como `feat:`, `fix:`, `chore:`, `refactor:` o equivalentes
- no usar formato `type(scope): descripción`
- no usar nombres de rama como título
- no usar títulos genéricos como `Update release contents`, `Apply several improvements`, `Technical changes` o equivalentes
- la frase principal debe representar el conjunto del merge, no un detalle menor
- la frase principal debe construirse a partir de los cambios principales reflejados en `"$ANALYSIS_FILE"`
- la frase principal debe agrupar los cambios más importantes del análisis, con un máximo de 5 ejes principales
- no debe convertirse en una enumeración mecánica de cambios
- debe priorizar los bloques funcionales o técnicos más relevantes y representativos del conjunto
- si existe un cambio claramente dominante, debe liderar la frase principal
- si existen varios cambios principales relacionados, deben agrupar de forma natural bajo una intención común
- si el análisis contiene muchos cambios heterogéneos, seleccionar únicamente los más importantes, con un máximo de 5
- no inventar funcionalidades, impacto ni alcance
- redactar la frase principal en inglés técnico natural y mantenible
- evitar lenguaje comercial o promocional
- priorizar estructuras del tipo:
  - verbo + área principal
  - verbo + área principal + and + segundo bloque agrupado
  - verbo + área principal + with + principales mejoras agrupadas

- la frase principal debe ser concisa
- no debe sonar a nombre de rama, commit convencional ni changelog
- no debe incluir punto final
- no debe superar 120 caracteres salvo necesidad justificada
- `MERGE_TITLE.txt` debe contener una única línea and sin bloque markdown

#### Criterio de selección de la frase principal

- identificar todos los bloques de cambio principales del análisis
- ordenarlos por relevancia funcional o técnica para la integración de la release
- seleccionar como máximo los 5 cambios más importantes
- agruparlos en una única intención clara y natural
- si algunos cambios son secundarios o redundantes respecto a otro bloque mayor, omitirlos
- si la frase pierde claridad por exceso de información, reducir el número de ejes hasta mantener una frase legible
- la frase principal debe resumir el conjunto del merge, no actuar como changelog

#### Reglas para `merge.txt`

- `merge.txt` debe contener únicamente el cuerpo del merge
- no debe incluir la frase principal del merge en la primera línea ni en ninguna otra parte salvo que aparezca citada de forma estrictamente necesaria
- queda prohibido duplicar la frase principal dentro del body
- el cuerpo es opcional; si no hay cambios clave adicionales claramente respaldados por el análisis, puede quedar vacío
- si se incluye contenido, debe ser exclusivamente en forma de viñetas breves
- cada viñeta debe estar respaldada explícitamente por `"$ANALYSIS_FILE"`
- cada viñeta debe ser breve, directa y basada en hechos
- no añadir secciones markdown como `##`, `###`, `Summary` o similares
- no añadir metadatos como versión, ramas o directorio dentro de `merge.txt`
- no añadir validaciones, riesgos, impacto, dependencias ni contexto no explícito
- no inventar categorías ni cambios
- no crear viñetas vacías
- mantener el contenido ultra compacto
- usar una idea por línea
- comenzar cada viñeta con `- `
- no repetir la misma idea en varias viñetas
- no convertir hipótesis del análisis en afirmaciones

Abortar si:

- no puede generarse una frase principal fiel al análisis
- `MERGE_TITLE.txt` contiene más de una línea
- `merge.txt` incluye la frase principal del merge dentro del body

---

### 6.4 Escribir MERGE_TITLE.txt y merge.txt

Crear o sobrescribir:

- `"$MERGE_TITLE_FILE"`
- `"$MERGE_FILE"`

Abortar si:

- no puede escribirse `"$MERGE_TITLE_FILE"`
- no puede escribirse `"$MERGE_FILE"`

---

### 6.5 Resultado de merge

Mostrar:

- `"$MERGE_TITLE_FILE"`
- `"$MERGE_FILE"`

Mostrar además un resumen breve indicando:

- frase principal del merge generada
- rama origen
- rama destino
- directorio de salida utilizado
- bloques principales incluidos realmente en base a `"$ANALYSIS_FILE"`
