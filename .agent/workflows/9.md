# Fase 2: Creación de Pull Request de develop hacia release

Este paso es crítico y debe ejecutarse con validación estricta de rama, obtención obligatoria de versión desde `package.json`, construcción controlada del título y cuerpo del Pull Request para una consolidación de release, ejecución controlada y validación obligatoria del enlace resultante.

## Objetivo

Preparar y, tras autorización explícita del usuario, ejecutar la creación del Pull Request desde `develop` hacia una rama `release/x.y.x`, obteniendo la versión real desde `package.json` y utilizando un título y cuerpo orientados a preparación de release.

Este Pull Request no debe tratarse como una feature pura. Debe tratarse como una consolidación técnica de release.

Reglas generales:

- la rama origen debe ser exactamente `develop`
- la versión debe obtenerse obligatoriamente desde `package.json`
- la rama destino debe derivarse a partir de la versión obtenida desde `package.json`
- este paso funciona en modo previsualización obligatoria
- antes de ejecutar cualquier comando, preguntar siempre al usuario y esperar autorización explícita
- no se podrá ejecutar ningún comando sin autorización explícita posterior del usuario
- la ejecución debe limitarse a un único comando por vez
- si el comando autorizado falla, detener inmediatamente el flujo
- si el comando autorizado falla, no reintentar, no corregir automáticamente y no ejecutar ningún otro comando adicional
- si el comando autorizado falla, mostrar el error y esperar nuevas instrucciones del usuario
- tras la ejecución autorizada, el resultado debe devolver un enlace válido de Pull Request
- dicho enlace debe guardarse obligatoriamente
- si no se obtiene un enlace válido y guardado, detener inmediatamente el flujo

---

### 8.1 Validar rama actual y obtener versión desde package.json

Leer las variables necesarias del fichero autorizado del flujo únicamente para metadatos mínimos y rutas de salida.

Objetivo:

Garantizar que el flujo parte exactamente desde `develop` y obtener la versión real declarada en `package.json` para derivar la rama destino release.

Validar obligatoriamente:

- `CURRENT_BRANCH` existe y no está vacía
- `CURRENT_BRANCH` es exactamente `develop`
- existe `package.json` y puede leerse
- puede obtenerse una versión real desde `package.json`
- la versión real obtenida desde `package.json` cumple exactamente el patrón `X.Y.Z`
- puede derivarse una rama destino válida `release/X.Y.x` a partir de la versión real obtenida desde `package.json`

Definir obligatoriamente:

- `PACKAGE_JSON_VERSION` = valor real leído desde `package.json`
- `RELEASE_VERSION` = `PACKAGE_JSON_VERSION`
- `TARGET_BRANCH="release/<X>.<Y>.x"`

Reglas:

- no aceptar ramas origen distintas de `develop`
- la rama destino release debe calcularse exclusivamente a partir de `package.json`
- no ejecutar ningún comando en este paso
- no crear Pull Request
- no cambiar de rama
- no hacer `push`
- no ejecutar comandos de Git, GitHub CLI o cualquier otra herramienta operativa sin preguntar antes al usuario
- este paso solo puede preparar una previsualización de validaciones y comandos

Abortar si:

- `CURRENT_BRANCH` no es exactamente `develop`
- `package.json` no existe o no puede leerse
- no puede obtenerse una versión real desde `package.json`
- no puede derivarse `TARGET_BRANCH`

Salida requerida:

- mostrar la rama actual detectada
- mostrar la versión real detectada en `package.json`
- mostrar la rama destino calculada a partir de `package.json`
- mostrar una previsualización de comprobaciones y comandos previstos
- indicar explícitamente que no se ha ejecutado ningún comando
- preguntar al usuario antes de cualquier ejecución real
- esperar autorización explícita del usuario antes de continuar

Ejemplo de obtención permitida de versión:

```bash
cat package.json
```

### 8.2 Construcción obligatoria del título y cuerpo del Pull Request

Objetivo:

Construir un Pull Request orientado a consolidación de release, no a feature.

Reglas:

- el título del Pull Request debe dejar clarísimo que es preparación de versión
- el cuerpo del Pull Request debe estar orientado a publicación de release
- el contenido debe adaptarse a la versión obtenida desde `package.json`
- no debe redactarse como una feature
- el merge commit futuro debe sonar a consolidación técnica de release y no a feature, aunque en este paso no se ejecuta ningún merge

Título permitido del Pull Request, adaptado a `RELEASE_VERSION`:

- `Prepare release <RELEASE_VERSION>`
- `Prepare VSIX release <RELEASE_VERSION>`
- `Stabilize release <RELEASE_VERSION>`

Título por defecto recomendado:

- `Prepare release <RELEASE_VERSION>`

Cuerpo obligatorio del Pull Request, adaptado a `RELEASE_VERSION`:

```md
## Summary
This PR prepares release <RELEASE_VERSION> for publication.

## Included scope
- Final version alignment in package.json
- Release notes and changelog updates
- VSIX packaging adjustments
- Final fixes required for publication

## Validation
- npm run lint
- npm run compile
- npm run test
- VSIX generated successfully
```

Referencia obligatoria para el merge commit futuro:

- `Prepare release <RELEASE_VERSION> for publication`
- `Stabilize <RELEASE_VERSION> release for publication`
- `Consolidate release <RELEASE_VERSION> changes`

Reglas adicionales:

- en este paso no se ejecuta merge alguno
- en este paso no se genera automáticamente el merge commit
- en este paso solo se construye el Pull Request con el estilo correcto de release

Salida requerida:

- mostrar el título previsto del Pull Request
- mostrar el cuerpo previsto del Pull Request
- mostrar la referencia prevista del merge commit futuro
- indicar explícitamente que no se ha ejecutado ningún comando

### 8.3 Crear Pull Request

Objetivo:

Preparar y, tras autorización explícita del usuario, ejecutar la creación del Pull Request desde `develop` hacia la rama `release/x.y.x` calculada desde `package.json`, utilizando el título y cuerpo adaptados a este tipo de Pull Request de consolidación de release.

Definir:

- rama origen: `develop`
- rama destino: `TARGET_BRANCH`
- título: `Prepare release <RELEASE_VERSION>`
- cuerpo: bloque release-oriented adaptado a `RELEASE_VERSION`
- `PR_LINK_FILE="$OUTPUT_DIR/PR_LINK.txt"`

Comando permitido:

```bash
gh pr create --base "$TARGET_BRANCH" --head develop --title "Prepare release <RELEASE_VERSION>" --body "<BODY_PR>"
```

Reglas:

- no inventar una rama destino distinta a la calculada desde `package.json`
- no redactar el Pull Request como una feature
- no ejecutar todavía el comando real de creación hasta obtener autorización explícita del usuario
- este paso solo debe mostrar la previsualización del comando exacto que se ejecutaría
- antes de ejecutar cualquier comando, preguntar al usuario
- solo está permitido ejecutar el comando exacto previamente mostrado en la previsualización y autorizado explícitamente por el usuario
- no está permitido ejecutar comandos alternativos, equivalentes, corregidos, abreviados o reconstruidos
- no está permitido encadenar comandos
- no está permitido ejecutar comandos auxiliares antes o después del comando aprobado
- no está permitido modificar argumentos, rutas, ramas, título o cuerpo sin nueva autorización explícita del usuario
- la ejecución debe ser siempre de un único comando por vez
- si el comando falla, detener inmediatamente el flujo
- si el comando falla, no ejecutar ningún otro comando posterior
- si el comando falla, no reintentar
- si el comando falla, no corregir automáticamente el comando
- si el comando falla, mostrar el error recibido y esperar nuevas instrucciones del usuario
- tras ejecutar el comando autorizado, el resultado debe contener un único enlace válido de Pull Request de GitHub
- el resultado válido debe seguir el patrón `https://github.com/<owner>/<repo>/pull/<number>`
- no se aceptan mensajes parciales, identificadores internos, texto descriptivo ni salidas sin enlace
- no se aceptan URLs de issues, commits, branches, compare, actions ni cualquier otro recurso distinto de un Pull Request
- el enlace obtenido debe guardarse obligatoriamente en `"$PR_LINK_FILE"`
- `"$PR_LINK_FILE"` debe contener únicamente una línea con la URL del Pull Request
- no está permitido continuar el flujo si no existe un enlace válido y guardado
- si la salida del comando no devuelve exactamente un enlace válido de Pull Request, detener inmediatamente el flujo
- si no puede escribirse `"$PR_LINK_FILE"`, detener inmediatamente el flujo
- si el enlace no puede validarse contra el patrón esperado, detener inmediatamente el flujo
- no reintentar automáticamente
- no ejecutar comandos adicionales para buscar el PR creado salvo nueva autorización explícita del usuario

Abortar si:

- no puede construirse una previsualización válida del Pull Request
- ya existe un Pull Request abierto con la misma rama origen y destino
- se intenta ejecutar un comando sin haber preguntado antes al usuario
- se intenta ejecutar un comando diferente al previamente autorizado
- se intenta ejecutar más de un comando
- el comando no devuelve una URL de Pull Request válida
- la URL no coincide con el patrón `https://github.com/<owner>/<repo>/pull/<number>`
- no puede guardarse `"$PR_LINK_FILE"`
- `"$PR_LINK_FILE"` queda vacío

Salida requerida:

- mostrar la operación prevista: creación de Pull Request `develop -> release/x.y.x`
- mostrar la versión calculada desde `package.json`
- mostrar la rama destino calculada desde `package.json`
- mostrar el título y cuerpo que se usarían
- mostrar el comando exacto que se ejecutaría para crear el Pull Request
- indicar explícitamente que no se ejecutará ningún otro comando adicional
- indicar explícitamente que no se ha ejecutado ningún comando
- avisar de que, si el comando falla o no devuelve un enlace válido de Pull Request, el flujo se detendrá inmediatamente
- preguntar al usuario antes de ejecutar la creación real del Pull Request
- tras ejecución autorizada y exitosa, mostrar el enlace del Pull Request creado
- mostrar la ruta de `"$PR_LINK_FILE"`
- indicar explícitamente que el enlace ha sido validado y guardado
- esperar autorización explícita del usuario para cualquier paso posterior
