# Flujo de publicación — Fases 2, 3 y 4

Este workflow cubre los pasos posteriores a la creación del Pull Request `release/1.Y.x → develop` (workflow `/61`).

Reglas globales:

- leer siempre las variables desde `"$VAR_S1_FILE"`
- leer siempre el enlace del PR desde `"$PR_LINK_FILE"` (`"$OUTPUT_DIR/PR_LINK.txt"`)
- leer siempre el título del merge desde `"$MERGE_TITLE_FILE"` (`"$OUTPUT_DIR/MERGE_TITLE.txt"`)
- leer siempre el cuerpo del merge desde `"$MERGE_FILE"` (`"$OUTPUT_DIR/merge.txt"`)
- no inventar variables, títulos, cuerpos ni enlaces
- no regenerar contenido ya producido por workflows anteriores
- antes de ejecutar cualquier comando, mostrar la previsualización y preguntar al usuario
- esperar autorización explícita antes de ejecutar cada comando
- ejecutar un único comando por vez
- si un comando falla, detener inmediatamente el flujo, mostrar el error y esperar instrucciones
- no reintentar, no corregir automáticamente, no encadenar comandos
- si cualquier fichero requerido no existe o está vacío, abortar el paso correspondiente

---

## Fase 2: Merge del Pull Request release/1.Y.x → develop

### 9.1 Validar estado previo al merge

Leer desde `"$VAR_S1_FILE"`:

- `OUTPUT_DIR`
- `CURRENT_BRANCH`
- `RELEASE_VERSION`
- `TARGET_BRANCH` (debe ser `develop`; si no existe, asumir `develop`)

Definir:

- `PR_LINK_FILE="$OUTPUT_DIR/PR_LINK.txt"`
- `MERGE_TITLE_FILE="$OUTPUT_DIR/MERGE_TITLE.txt"`
- `MERGE_FILE="$OUTPUT_DIR/merge.txt"`
- `MERGE_MESSAGE_FILE="$OUTPUT_DIR/MERGE_MESSAGE.txt"`

Validar obligatoriamente:

- `PR_LINK_FILE` existe y contiene una URL válida con el patrón `https://github.com/<owner>/<repo>/pull/<number>`
- `MERGE_TITLE_FILE` existe y no está vacío
- `MERGE_FILE` existe (puede estar vacío si no hay viñetas adicionales)
- extraer `PR_NUMBER` desde el enlace de `"$PR_LINK_FILE"`

Abortar si:

- `"$PR_LINK_FILE"` no existe
- `"$PR_LINK_FILE"` está vacío
- el contenido de `"$PR_LINK_FILE"` no coincide con el patrón esperado
- `PR_NUMBER` no puede extraerse
- `"$MERGE_TITLE_FILE"` no existe o está vacío

Salida requerida:

- mostrar el enlace del PR leído
- mostrar el número de PR extraído
- mostrar el título del merge previsto desde `"$MERGE_TITLE_FILE"`
- mostrar el cuerpo del merge previsto desde `"$MERGE_FILE"`
- indicar explícitamente que no se ha ejecutado ningún comando

---

### 9.2 Construir mensaje de merge

Objetivo:

Construir el mensaje de merge commit completo combinando `"$MERGE_TITLE_FILE"` y `"$MERGE_FILE"`, siguiendo la convención editorial del proyecto.

El mensaje de merge debe seguir la estructura:

```text
<contenido de MERGE_TITLE.txt> #<PR_NUMBER>

<contenido de merge.txt, si no está vacío>
```

Reglas:

- la primera línea debe ser exactamente: contenido de `"$MERGE_TITLE_FILE"` seguido de ` #<PR_NUMBER>`
- si `"$MERGE_FILE"` tiene contenido, incluirlo separado por una línea en blanco
- si `"$MERGE_FILE"` está vacío, el mensaje de merge solo contiene la primera línea
- no inventar viñetas ni contenido adicional
- no añadir prefijos como `Merge pull request`, `feat:`, `fix:` ni equivalentes
- no añadir metadatos de rama, versión ni fecha dentro del mensaje

Acción:

Escribir el resultado en `"$MERGE_MESSAGE_FILE"`.

Abortar si:

- no puede construirse el mensaje siguiendo estas reglas
- no puede escribirse `"$MERGE_MESSAGE_FILE"`

Salida requerida:

- mostrar el contenido exacto de `"$MERGE_MESSAGE_FILE"`
- indicar explícitamente que no se ha ejecutado ningún comando de merge

---

### 9.3 Hacer merge del Pull Request

Objetivo:

Preparar y, tras autorización explícita del usuario, ejecutar el merge del Pull Request usando el mensaje personalizado de `"$MERGE_MESSAGE_FILE"`.

Definir:

- el número de PR: `PR_NUMBER` (extraído en 9.1 desde `"$PR_LINK_FILE"`)
- método de merge: `--merge` (merge commit estándar)
- fichero de mensaje: `"$MERGE_MESSAGE_FILE"`

Reglas:

- no usar squash ni rebase salvo autorización explícita del usuario en este paso
- no usar el mensaje por defecto de GitHub CLI
- el título y cuerpo del merge deben provenir exclusivamente de `"$MERGE_MESSAGE_FILE"`
- no alterar el número de PR
- no crear un nuevo PR
- no hacer push adicional
- no ejecutar ningún otro comando auxiliar antes ni después del comando autorizado

Previsualización del comando a ejecutar:

```bash
gh pr merge <PR_NUMBER> --merge --subject "<línea 1 de MERGE_MESSAGE_FILE>" --body "<resto de MERGE_MESSAGE_FILE>"
```

Nota: si `gh pr merge` no soporta `--subject` y `--body`, usar la alternativa de `--body-file`:

```bash
gh pr merge <PR_NUMBER> --merge --body-file "<ruta absoluta a MERGE_MESSAGE_FILE>"
```

Mostrar el comando exacto que se ejecutaría con los valores reales antes de pedir autorización.

Abortar si:

- `PR_NUMBER` no está definido o no es válido
- `"$MERGE_MESSAGE_FILE"` no existe o está vacío
- se intenta ejecutar sin autorización explícita del usuario
- el comando falla → detener inmediatamente, mostrar el error, esperar instrucciones

Salida requerida tras ejecución autorizada:

- mostrar la salida del comando
- indicar que el merge se ha completado
- esperar autorización explícita del usuario para continuar a la Fase 3

## Fase 3: Pull Request release/1.Y.x → main

### 10.1 Validar fuentes para el PR hacia main

El PR hacia main tiene un propósito distinto al PR hacia develop: es la **publicación oficial** de la release. Su título y cuerpo deben seguir la convención del proyecto para este flujo.

Leer desde `"$VAR_S1_FILE"`:

- `OUTPUT_DIR`
- `CURRENT_BRANCH` (debe seguir siendo `release/1.Y.x`)
- `RELEASE_VERSION`
- `REPOWN` (propietario del repositorio)

Definir:

- `PR_MAIN_TITLE_FILE="$OUTPUT_DIR/PR_MAIN_TITLE.txt"`
- `PR_MAIN_FILE="$OUTPUT_DIR/PR_MAIN.txt"`
- `PR_MAIN_LINK_FILE="$OUTPUT_DIR/PR_MAIN_LINK.txt"`

Reglas de contenido para este PR (convención del proyecto):

#### Título (`PR_MAIN_TITLE_FILE`)

Formato: `Publish release <RELEASE_VERSION>`

Ejemplo: `Publish release 1.3.49`

#### Cuerpo (`PR_MAIN_FILE`)

Formato obligatorio:

```markdown
## Summary
This PR publishes version <RELEASE_VERSION> to main.

## Release highlights
<viñetas extraídas de MERGE_TITLE.txt y merge.txt — los puntos más visibles>

## Release artifacts
- VSIX package ready for GitHub Release

## Validation
- npm run lint
- npm run compile
- npm run test
- VSIX built and verified
```

Reglas:

- `Release highlights` debe construirse a partir del contenido de `"$MERGE_TITLE_FILE"` y `"$MERGE_FILE"`, no inventar
- si `"$MERGE_FILE"` está vacío, extraer los puntos del título
- no duplicar el título dentro del body
- no añadir secciones no respaldadas por el análisis anterior

Acción:

Escribir `"$PR_MAIN_TITLE_FILE"` y `"$PR_MAIN_FILE"`.

Abortar si:

- `RELEASE_VERSION` no existe o está vacío
- `"$MERGE_TITLE_FILE"` no existe o está vacío
- no puede construirse el contenido

Salida requerida:

- mostrar el título previsto del PR hacia main
- mostrar el cuerpo previsto del PR hacia main
- indicar que no se ha ejecutado ningún comando

---

### 10.2 Crear Pull Request release/1.Y.x → main

Objetivo:

Preparar y, tras autorización explícita del usuario, crear el Pull Request desde la rama actual `release/1.Y.x` hacia `main`.

Reglas:

- rama origen: `CURRENT_BRANCH` (`release/1.Y.x`)
- rama destino: `main`
- título: contenido exacto de `"$PR_MAIN_TITLE_FILE"`
- cuerpo: contenido exacto de `"$PR_MAIN_FILE"`
- si ya existe un PR abierto con la misma rama origen y destino, no duplicarlo → abortar
- antes de ejecutar, mostrar la previsualización y preguntar al usuario
- tras ejecución exitosa, guardar el enlace del PR en `"$PR_MAIN_LINK_FILE"`
- `"$PR_MAIN_LINK_FILE"` debe contener únicamente una línea con la URL del PR

Comando previsto:

```bash
gh pr create --base main --head <CURRENT_BRANCH> --title "<contenido de PR_MAIN_TITLE_FILE>" --body-file "<ruta absoluta a PR_MAIN_FILE>"
```

Abortar si:

- el comando falla → detener inmediatamente, mostrar error, esperar instrucciones
- la salida no devuelve una URL válida con patrón `https://github.com/<owner>/<repo>/pull/<number>`
- no puede guardarse `"$PR_MAIN_LINK_FILE"`

Salida requerida:

- mostrar el enlace del PR hacia main creado
- confirmar que el enlace ha sido validado y guardado en `"$PR_MAIN_LINK_FILE"`
- esperar autorización explícita del usuario para continuar

---

### 10.3 Merge del Pull Request hacia main

Objetivo:

Preparar y, tras autorización explícita del usuario, hacer merge del PR hacia main con mensaje editorial.

El mensaje de merge hacia main sigue la convención editorial del proyecto, y es el más importante del historial de publicación.

Definir:

- `PR_MAIN_NUMBER`: extraído de `"$PR_MAIN_LINK_FILE"`
- `MERGE_MAIN_MESSAGE_FILE="$OUTPUT_DIR/MERGE_MAIN_MESSAGE.txt"`

Construir el mensaje de merge hacia main con este formato:

```text
<contenido de MERGE_TITLE.txt> #<PR_MAIN_NUMBER>

<contenido de merge.txt, si no está vacío>
```

Reglas:

- la primera línea es: contenido de `"$MERGE_TITLE_FILE"` + ` #<PR_MAIN_NUMBER>`
- si `"$MERGE_FILE"` tiene contenido, incluirlo tras una línea en blanco
- no añadir prefijos de merge automáticos
- escribir el resultado en `"$MERGE_MAIN_MESSAGE_FILE"`

Comando previsto para el merge:

```bash
gh pr merge <PR_MAIN_NUMBER> --merge --body-file "<ruta absoluta a MERGE_MAIN_MESSAGE_FILE>"
```

Abortar si:

- `PR_MAIN_NUMBER` no puede extraerse
- `"$MERGE_MAIN_MESSAGE_FILE"` no puede escribirse
- el comando falla → detener, mostrar error, esperar instrucciones

Salida requerida:

- mostrar el mensaje de merge previsto
- mostrar el comando exacto que se ejecutaría
- tras ejecución exitosa, confirmar el merge completado
- esperar autorización explícita del usuario para continuar a la Fase 4

## Fase 4: Back-merge main → develop

### 11.1 Validar estado para el back-merge

Leer desde `"$VAR_S1_FILE"`:

- `RELEASE_VERSION`
- `REPOWN`

Validar:

- el PR hacia main ha sido mergeado (confirmado por el usuario al final de 10.3)
- la rama actual es `release/1.Y.x` o `main` (ambas son válidas como punto de partida)

Definir:

- `PR_BACKMM_TITLE_FILE="$OUTPUT_DIR/PR_BACKMERGE_TITLE.txt"`
- `PR_BACKMERGE_FILE="$OUTPUT_DIR/PR_BACKMERGE.txt"`
- `PR_BACKMERGE_LINK_FILE="$OUTPUT_DIR/PR_BACKMERGE_LINK.txt"`

Contenido del PR de back-merge:

#### Título (`PR_BACKMERGE_TITLE_FILE`)

Formato: `Sync main back into develop after release <RELEASE_VERSION>`

#### Cuerpo (`PR_BACKMERGE_FILE`)

Formato:

```markdown
## Summary
This PR syncs main back into develop after publishing version <RELEASE_VERSION>.

## Purpose
- Keep develop aligned with the published release
- Preserve changelog, release notes, and versioning updates
```

Abortar si:

- `RELEASE_VERSION` no existe o está vacío

Salida requerida:

- mostrar título y cuerpo previstos del PR de back-merge
- indicar que no se ha ejecutado ningún comando
