# Fase 2: Creación de Pull Request de develop hacia release

Este paso es crítico y debe ejecutarse con validación estricta de ramas, cálculo obligatorio de versión y rama release a partir de `package.json`, validación de consistencia del diff, revisión de cambios respecto al mergeo aprobado del paso 61, estado limpio del repositorio, fuentes permitidas, ejecución controlada y validación obligatoria del enlace resultante.

## Objetivo

Preparar y, tras autorización explícita del usuario, ejecutar la creación del Pull Request desde `develop` hacia una rama `release/x.y.x`, utilizando exclusivamente los ficheros generados para título y cuerpo del Pull Request.

Además, antes de cualquier creación real, este paso debe:

- calcular la versión real de la release a partir de la versión declarada en `package.json`
- derivar de forma obligatoria el nombre de la rama destino `release/x.y.x` a partir de esa versión
- comprobar si han aparecido cambios nuevos respecto al diff aprobado previamente
- comprobar si han aparecido cambios respecto al contexto del mergeo aprobado del paso 61
- si aparecen cambios, generar contenido actualizado de PR y merge en archivos nuevos sin sobrescribir los originales

Reglas generales:

- la rama origen debe ser exactamente `develop`
- la rama destino debe ser una rama `release/x.y.x` calculada a partir de `package.json`
- la versión de release debe calcularse obligatoriamente desde `package.json`
- no está permitido fijar manualmente `RELEASE_VERSION` si contradice el valor real de `package.json`
- no está permitido fijar manualmente `TARGET_BRANCH` si contradice la rama calculada desde `package.json`
- el título del Pull Request debe provenir exclusivamente de `PR_TITLE.txt` o, si aplica por refresco, de `PR_TITLE_REFRESH.txt`
- el cuerpo del Pull Request debe provenir exclusivamente de `PR.txt` o, si aplica por refresco, de `PR_REFRESH.txt`
- no está permitido regenerar manualmente el contenido del Pull Request fuera de los archivos refresh previstos en este paso
- este paso funciona en modo previsualización obligatoria
- antes de ejecutar cualquier comando, preguntar siempre al usuario y esperar autorización explícita
- no se podrá ejecutar ningún comando sin autorización explícita posterior del usuario
- la ejecución debe limitarse a un único comando por vez
- si el comando autorizado falla, detener inmediatamente el flujo
- si el comando autorizado falla, no reintentar, no corregir automáticamente y no ejecutar ningún otro comando adicional
- si el comando autorizado falla, mostrar el error y esperar nuevas instrucciones del usuario
- tras la ejecución autorizada, el resultado debe devolver un enlace válido de Pull Request
- dicho enlace debe guardarse obligatoriamente
- si no se obtiene un enlace válido y guardado, detener inmediatamente el flujo

### 8.1 Validar rama actual, calcular versión desde package.json, validar diff de referencia y estado seguro del repositorio

Leer las variables necesarias del fichero autorizado del flujo.

Objetivo:

Garantizar que el flujo parte de una rama válida, que existe un diff previo aprobado, que la versión y la rama release se calculan desde `package.json` y que no existen cambios locales pendientes relevantes antes de preparar ninguna operación.

Validar obligatoriamente:

- `CURRENT_BRANCH` existe y no está vacía
- `CURRENT_BRANCH` es exactamente `develop`
- `DIFF_FILE` existe y no está vacío
- existe `package.json` y puede leerse
- puede obtenerse una versión real desde `package.json`
- la versión real obtenida desde `package.json` cumple exactamente el patrón `X.Y.Z`
- `RELEASE_VERSION` existe y no está vacía
- `RELEASE_VERSION` coincide exactamente con la versión real obtenida desde `package.json`
- puede derivarse una rama destino válida `release/X.Y.x` a partir de la versión real obtenida desde `package.json`
- si `TARGET_BRANCH` existe, debe coincidir exactamente con la rama derivada desde `package.json`
- no hay archivos modificados sin commit que afecten al flujo
- no hay archivos staged pendientes de commit que afecten al flujo
- no hay archivos untracked que afecten al flujo

Definir obligatoriamente:

- `PACKAGE_JSON_VERSION` = valor real de `package.json`
- `RELEASE_VERSION` = `PACKAGE_JSON_VERSION`
- `TARGET_BRANCH_CALCULATED="release/<X>.<Y>.x"`
- `TARGET_BRANCH` = `TARGET_BRANCH_CALCULATED`

Reglas:

- no aceptar ramas origen distintas de `develop`
- no aceptar ramas destino distintas de `release/x.y.x`
- la rama release debe calcularse exclusivamente a partir de `package.json`
- no usar nombres de rama escritos manualmente si contradicen el cálculo desde `package.json`
- para validar el estado local, deben ignorarse explícitamente los directorios `.agent/**` y `out_tmp/**`
- los cambios dentro de `.agent/**` y `out_tmp/**` no deben bloquear el flujo
- cualquier otro cambio local fuera de esas rutas sí debe bloquear el flujo
- no ejecutar ningún comando en este paso
- no crear Pull Request
- no cambiar de rama
- no hacer `push`
- no ejecutar comandos de Git, GitHub CLI o cualquier otra herramienta operativa sin preguntar antes al usuario
- este paso solo puede preparar una previsualización de validaciones y comandos
- si existen cambios sin commit fuera de `.agent/**` y `out_tmp/**`, el flujo debe detenerse antes de cualquier operación

Abortar si:

- `CURRENT_BRANCH` no es exactamente `develop`
- `package.json` no existe o no puede leerse
- no puede obtenerse una versión real desde `package.json`
- `RELEASE_VERSION` no coincide con la versión real de `package.json`
- no puede derivarse `TARGET_BRANCH_CALCULATED`
- `TARGET_BRANCH` existe y no coincide exactamente con la rama calculada desde `package.json`
- falta cualquiera de los datos obligatorios
- `"$DIFF_FILE"` no existe o está vacío
- existe cualquier cambio local sin commit fuera de `.agent/**` y `out_tmp/**`
- existe cualquier cambio staged pendiente fuera de `.agent/**` y `out_tmp/**`
- existen archivos untracked que comprometen el flujo fuera de `.agent/**` y `out_tmp/**`
- se intenta ejecutar un comando sin haber preguntado antes al usuario
- se intenta ejecutar un comando sin autorización explícita del usuario

Salida requerida:

- mostrar el estado del árbol de trabajo
- mostrar la rama actual detectada
- mostrar la versión real detectada en `package.json`
- mostrar la rama destino calculada a partir de `package.json`
- mostrar el diff de referencia que se usará para la validación
- mostrar una previsualización de comprobaciones y comandos previstos
- indicar explícitamente que no se ha ejecutado ningún comando
- preguntar al usuario antes de cualquier ejecución real
- esperar autorización explícita del usuario antes de continuar

### 8.2 Validación obligatoria de consistencia del diff y revisión respecto al mergeo del paso 61

Está permitido leer únicamente:

- `"$DIFF_FILE"` como diff de referencia aprobado para esta fase
- `"$VAR_S1_FILE"` para obtener variables del flujo y el rango lógico del diff
- `"$PR_TITLE_FILE"`, `"$PR_FILE"`, `"$MERGE_TITLE_FILE"` y `"$MERGE_FILE"` como archivos base ya generados
- la referencia aprobada del paso 61 únicamente si está explícitamente declarada en `"$VAR_S1_FILE"`

Objetivo:

Comprobar simultáneamente:

- si el diff vigente del flujo sigue siendo consistente o si han aparecido cambios nuevos respecto al diff aprobado previamente
- si el contenido actual ha cambiado respecto al mergeo aprobado del paso 61

Definir obligatoriamente:

- `NEW_DIFF_FILE="$OUTPUT_DIR/diffs_regenerated.txt"`
- `DIFF_COMPARE_FILE="$OUTPUT_DIR/diff_compare.txt"`
- `STEP61_BASELINE_FILE` = referencia explícita del paso 61 declarada en `"$VAR_S1_FILE"`
- `STEP61_COMPARE_FILE="$OUTPUT_DIR/step61_merge_compare.txt"`
- `PR_TITLE_REFRESH_FILE="$OUTPUT_DIR/PR_TITLE_REFRESH.txt"`
- `PR_REFRESH_FILE="$OUTPUT_DIR/PR_REFRESH.txt"`
- `MERGE_TITLE_REFRESH_FILE="$OUTPUT_DIR/MERGE_TITLE_REFRESH.txt"`
- `MERGE_REFRESH_FILE="$OUTPUT_DIR/MERGE_REFRESH.txt"`

Reglas:

- el nuevo diff debe generarse usando exactamente el mismo rango lógico del flujo original
- el nuevo diff debe guardarse obligatoriamente en `"$NEW_DIFF_FILE"`
- la comparación entre el diff original y el nuevo diff debe guardarse obligatoriamente en `"$DIFF_COMPARE_FILE"`
- la comparación respecto al mergeo aprobado del paso 61 debe guardarse obligatoriamente en `"$STEP61_COMPARE_FILE"`
- la comparación debe realizarse sobre contenido completo del fichero, no sobre fechas, tamaño o metadatos
- la referencia del paso 61 debe ser explícita; no está permitido inferirla desde el historial conversacional
- si no existe referencia explícita del paso 61 en `"$VAR_S1_FILE"`, el flujo debe abortar
- si el diff original y el nuevo diff son equivalentes y no hay diferencias respecto al paso 61, no deben generarse archivos refresh
- si el diff original y el nuevo diff son distintos, o si hay diferencias respecto al mergeo del paso 61, deben generarse los archivos refresh y no deben sobrescribirse los archivos originales
- no está permitido modificar `"$PR_TITLE_FILE"`, `"$PR_FILE"`, `"$MERGE_TITLE_FILE"` ni `"$MERGE_FILE"`
- el contenido refresh debe quedar aislado en archivos nuevos

Comportamiento obligatorio si no hay cambios nuevos:

- usar `"$PR_TITLE_FILE"` y `"$PR_FILE"` como fuente final del Pull Request
- conservar `"$MERGE_TITLE_FILE"` y `"$MERGE_FILE"` sin cambios
- no generar archivos refresh

Comportamiento obligatorio si sí hay cambios nuevos respecto al diff o al paso 61:

- no sobrescribir los archivos originales
- generar `"$PR_TITLE_REFRESH_FILE"` y `"$PR_REFRESH_FILE"`
- generar `"$MERGE_TITLE_REFRESH_FILE"` y `"$MERGE_REFRESH_FILE"`
- indicar explícitamente si el cambio proviene del diff regenerado, del contraste con el paso 61 o de ambos
- indicar explícitamente que estos archivos refresh sustituyen solo para esta ejecución a los archivos originales
- el título refresh del PR debe seguir la convención exacta `Prepare release x.y.z`
- el título refresh del merge debe seguir la convención exacta `Prepare release x.y.z for publication`

Abortar si:

- no puede generarse el nuevo diff de control
- no puede generarse la comparación de diff
- no existe referencia explícita y verificable del paso 61
- no puede generarse la comparación respecto al paso 61
- hay cambios nuevos y no pueden generarse correctamente los archivos refresh requeridos
- se intenta sobrescribir alguno de los archivos originales

Salida requerida:

- mostrar la ruta del diff original
- mostrar la ruta del diff regenerado
- mostrar la ruta del fichero de comparación del diff
- mostrar la ruta del fichero de comparación respecto al paso 61
- indicar si se han detectado o no cambios nuevos respecto al diff aprobado
- indicar si se han detectado o no cambios respecto al mergeo aprobado del paso 61
- si hay cambios nuevos, mostrar los archivos refresh generados
- indicar explícitamente que no se ha ejecutado ningún comando de creación real del Pull Request

### 8.3 Fuente obligatoria para el Pull Request

Está permitido leer únicamente:

- `"$PR_TITLE_FILE_FINAL"` como título final del Pull Request para esta ejecución
- `"$PR_FILE_FINAL"` como cuerpo final del Pull Request para esta ejecución
- `"$VAR_S1_FILE"` para validaciones de contexto y metadatos mínimos

Donde:

- `PR_TITLE_FILE_FINAL` apunta a `"$PR_TITLE_FILE"` si no hubo cambios nuevos
- `PR_TITLE_FILE_FINAL` apunta a `"$PR_TITLE_REFRESH_FILE"` si hubo cambios nuevos
- `PR_FILE_FINAL` apunta a `"$PR_FILE"` si no hubo cambios nuevos
- `PR_FILE_FINAL` apunta a `"$PR_REFRESH_FILE"` si hubo cambios nuevos

No está permitido usar ninguna otra fuente para construir el Pull Request.

Reglas:

- el Pull Request debe usar como título exactamente el contenido de `"$PR_TITLE_FILE_FINAL"`
- el Pull Request debe usar como cuerpo exactamente el contenido de `"$PR_FILE_FINAL"`
- no resumir de nuevo el análisis
- no rehacer el título
- no rehacer el cuerpo
- no añadir bloques nuevos no presentes en los ficheros generados
- no modificar el contenido salvo ajustes estrictamente técnicos de formato si el sistema de creación del Pull Request lo exige
- si el fichero final de título no existe o está vacío, abortar
- si el fichero final de cuerpo no existe o está vacío, abortar
- no ejecutar todavía ningún comando de creación real
- este paso solo debe preparar una previsualización

Abortar si:

- `"$PR_TITLE_FILE_FINAL"` no existe
- `"$PR_TITLE_FILE_FINAL"` está vacío
- `"$PR_FILE_FINAL"` no existe
- `"$PR_FILE_FINAL"` está vacío
- no puede obtenerse un título válido desde `"$PR_TITLE_FILE_FINAL"`
- no puede obtenerse un cuerpo válido desde `"$PR_FILE_FINAL"`

Salida requerida:

- mostrar el título previsto del Pull Request
- mostrar el cuerpo previsto del Pull Request
- mostrar la rama origen prevista
- mostrar la rama destino prevista calculada desde `package.json`
- indicar si la fuente final es original o refresh
- indicar explícitamente que no se ha ejecutado ningún comando

### 8.4 Crear Pull Request

Objetivo:

Preparar y, tras autorización explícita del usuario, ejecutar la creación del Pull Request desde `develop` hacia la rama `release/x.y.x` calculada desde `package.json`, utilizando exclusivamente el contenido final de `"$PR_TITLE_FILE_FINAL"` y `"$PR_FILE_FINAL"`.

Definir:

- rama origen: `develop`
- rama destino: `TARGET_BRANCH`
- título: contenido de `"$PR_TITLE_FILE_FINAL"`
- cuerpo: contenido de `"$PR_FILE_FINAL"`
- `PR_LINK_FILE="$OUTPUT_DIR/PR_LINK.txt"`

Reglas:

- no inventar título
- no inventar cuerpo
- no alterar la rama destino calculada desde `package.json`
- no crear el Pull Request contra otra rama distinta de `TARGET_BRANCH`
- si ya existe un Pull Request abierto con la misma rama origen y destino, no duplicarlo
- no ejecutar todavía el comando real de creación hasta obtener autorización explícita del usuario
- este paso solo debe mostrar la previsualización del comando exacto que se ejecutaría
- antes de ejecutar cualquier comando, preguntar al usuario
- solo está permitido ejecutar el comando exacto previamente mostrado en la previsualización y autorizado explícitamente por el usuario
- no está permitido ejecutar comandos alternativos, equivalentes, corregidos, abreviados o reconstruidos
- no está permitido encadenar comandos
- no está permitido ejecutar comandos auxiliares antes o después del comando aprobado
- no está permitido modificar argumentos, rutas, ramas, título o `body-file` sin nueva autorización explícita del usuario
- la ejecución debe ser siempre de un único comando por vez
- si el comando falla, detener inmediatamente el flujo
- si el comando falla, no ejecutar ningún otro comando posterior
- si el comando falla, no reintentar
- si el comando falla, no corregir automáticamente el comando
- si el comando falla, mostrar el error recibido y esperar nuevas instrucciones del usuario
- tras ejecutar el comando autorizado, el resultado debe contener un único enlace válido de Pull Request de GitHub
- el resultado válido debe seguir el patrón `https://github.com/<owner>/<repo>/pull/<number>`
- no se aceptan mensajes parciales, identificadores internos, texto descriptivo ni salidas sin enlace
- no se aceptan URLs de issues, commits, branches, compare, actions ni cualquier otro recurso distinto de un Pull Request
- el enlace obtenido debe guardarse obligatoriamente en `"$PR_LINK_FILE"`
- `"$PR_LINK_FILE"` debe contener únicamente una línea con la URL del Pull Request
- no está permitido continuar el flujo si no existe un enlace válido y guardado
- si la salida del comando no devuelve exactamente un enlace válido de Pull Request, detener inmediatamente el flujo
- si no puede escribirse `"$PR_LINK_FILE"`, detener inmediatamente el flujo
- si el enlace no puede validarse contra el patrón esperado, detener inmediatamente el flujo
- no reintentar automáticamente
- no ejecutar comandos adicionales para buscar el PR creado salvo nueva autorización explícita del usuario

Abortar si:

- no puede obtenerse correctamente el título desde `"$PR_TITLE_FILE_FINAL"`
- no puede obtenerse correctamente el cuerpo desde `"$PR_FILE_FINAL"`
- no puede construirse una previsualización válida del Pull Request
- ya existe un Pull Request abierto con la misma rama origen y destino
- se intenta ejecutar un comando sin haber preguntado antes al usuario
- se intenta ejecutar un comando diferente al previamente autorizado
- se intenta ejecutar más de un comando
- el comando no devuelve una URL de Pull Request válida
- la URL no coincide con el patrón `https://github.com/<owner>/<repo>/pull/<number>`
- no puede guardarse `"$PR_LINK_FILE"`
- `"$PR_LINK_FILE"` queda vacío

Salida requerida:

- mostrar la operación prevista: creación de Pull Request `develop -> release/x.y.x`
- mostrar la versión calculada desde `package.json`
- mostrar la rama destino calculada desde `package.json`
- mostrar el título y cuerpo que se usarían
- mostrar el comando exacto que se ejecutaría para crear el Pull Request
- indicar explícitamente que no se ejecutará ningún otro comando adicional
- indicar explícitamente que no se ha ejecutado ningún comando
- avisar de que, si el comando falla o no devuelve un enlace válido de Pull Request, el flujo se detendrá inmediatamente
- preguntar al usuario antes de ejecutar la creación real del Pull Request
- tras ejecución autorizada y exitosa, mostrar el enlace del Pull Request creado
- mostrar la ruta de `"$PR_LINK_FILE"`
- indicar explícitamente que el enlace ha sido validado y guardado
- esperar autorización explícita del usuario para cualquier paso posterior

Ejemplo de comando permitido:

`gh pr create --base "$TARGET_BRANCH" --head develop --title "$(cat \"$PR_TITLE_FILE_FINAL\")" --body-file "$PR_FILE_FINAL"`

Reglas sobre el ejemplo:

- si este es el comando aprobado por el usuario, solo puede ejecutarse exactamente este
- si falla, detener el flujo inmediatamente
- no ejecutar después comandos como `gh pr view`, `gh pr edit`, `git status`, `git push` o similares salvo nueva autorización explícita
