## Fase 1: Cierre del Pull Request mediante merge hacia develop

Este paso es crítico y debe ejecutarse con validación estricta del Pull Request, estado limpio del repositorio, fuentes permitidas, ejecución controlada y validación obligatoria del resultado del merge.

### Objetivo

Preparar y, tras autorización explícita del usuario, ejecutar el merge del Pull Request aprobado desde una rama `release/1.Y.x` hacia `develop`, utilizando exclusivamente los ficheros generados para la frase principal y el cuerpo del merge.

Reglas generales:

- el Pull Request a mergear debe corresponder a la fase 1 `release/1.Y.x -> develop`
- la rama destino del merge debe ser exactamente `develop`
- la frase principal del merge debe provenir exclusivamente de `MERGE_TITLE.txt`
- el cuerpo del merge debe provenir exclusivamente de `merge.txt`
- el enlace del Pull Request debe provenir exclusivamente de `PR_LINK.txt`
- no está permitido regenerar manualmente el contenido del merge en este paso
- este paso funciona en modo previsualización obligatoria
- antes de ejecutar cualquier comando, preguntar siempre al usuario y esperar autorización explícita
- no se podrá ejecutar ningún comando sin autorización explícita posterior del usuario
- la ejecución debe limitarse a un único comando por vez
- si el comando autorizado falla, detener inmediatamente el flujo
- si el comando autorizado falla, no reintentar, no corregir automáticamente y no ejecutar ningún otro comando adicional
- si el comando autorizado falla, mostrar el error y esperar nuevas instrucciones del usuario
- tras la ejecución autorizada, el resultado del merge debe ser válido y verificable
- si no se obtiene un resultado válido del merge, detener inmediatamente el flujo

---

### 9.1 Validar estado previo al merge

Leer las variables necesarias del fichero autorizado del flujo.

Objetivo:

Garantizar que el Pull Request correcto existe, que el repositorio no tiene cambios locales relevantes y que el merge puede prepararse de forma segura.

Validar obligatoriamente:

- `CURRENT_BRANCH` existe y no está vacía
- `CURRENT_BRANCH` cumple exactamente la expresión `^release/1\.[0-9]+\.x$`
- `PR_LINK_FILE` existe y no está vacío
- `PR_LINK_FILE` contiene una URL válida con el patrón `https://github.com/<owner>/<repo>/pull/<number>`
- no hay archivos modificados sin commit que afecten al flujo
- no hay archivos staged pendientes de commit que afecten al flujo
- no hay archivos untracked que afecten al flujo

Reglas:

- para validar el estado local, deben ignorarse explícitamente los directorios `.agent/**` y `out_tmp/**`
- los cambios dentro de `.agent/**` y `out_tmp/**` no deben bloquear el flujo
- cualquier otro cambio local fuera de esas rutas sí debe bloquear el flujo
- no ejecutar ningún comando en este paso
- no hacer merge
- no cambiar de rama
- no hacer `push`
- no ejecutar comandos de Git, GitHub CLI o cualquier otra herramienta operativa sin preguntar antes al usuario
- este paso solo puede preparar una previsualización de validaciones y comandos
- si existen cambios sin commit fuera de `.agent/**` y `out_tmp/**`, el flujo debe detenerse antes de cualquier operación

Abortar si:

- `CURRENT_BRANCH` no cumple la expresión `^release/1\.[0-9]+\.x$`
- `PR_LINK_FILE` no existe
- `PR_LINK_FILE` está vacío
- el contenido de `PR_LINK_FILE` no es una URL válida de Pull Request
- existe cualquier cambio local sin commit fuera de `.agent/**` y `out_tmp/**`
- existe cualquier cambio staged pendiente fuera de `.agent/**` y `out_tmp/**`
- existen archivos untracked que comprometen el flujo fuera de `.agent/**` y `out_tmp/**`
- se intenta ejecutar un comando sin haber preguntado antes al usuario
- se intenta ejecutar un comando sin autorización explícita del usuario

Salida requerida:

- mostrar el estado del árbol de trabajo
- mostrar la rama actual detectada
- mostrar el enlace del Pull Request detectado
- mostrar la rama destino prevista: `develop`
- mostrar una previsualización de comprobaciones y comandos previstos
- indicar explícitamente que no se ha ejecutado ningún comando
- preguntar al usuario antes de cualquier ejecución real
- esperar autorización explícita del usuario antes de continuar

### 9.2 Fuente obligatoria para el merge

Está permitido leer únicamente:

- `"$MERGE_TITLE_FILE"` como frase principal del merge
- `"$MERGE_FILE"` como cuerpo del merge
- `"$PR_LINK_FILE"` como enlace del Pull Request a cerrar
- `"$VAR_S1_FILE"` para validaciones de contexto y metadatos mínimos

No está permitido usar ninguna otra fuente para construir el merge.

Definir:

- `MERGE_MESSAGE_FILE="$OUTPUT_DIR/MERGE_MESSAGE.txt"`

Reglas:

- la frase principal del merge debe provenir exclusivamente de `"$MERGE_TITLE_FILE"`
- el cuerpo del merge debe provenir exclusivamente de `"$MERGE_FILE"`
- el Pull Request a mergear debe obtenerse exactamente desde `"$PR_LINK_FILE"`
- dado que `gh pr merge` no admite `--subject`, debe construirse un único fichero de mensaje para merge
- `MERGE_MESSAGE_FILE` debe componerse así:
  - primera línea: contenido de `"$MERGE_TITLE_FILE"`
  - una línea en blanco
  - después: contenido de `"$MERGE_FILE"` si no está vacío
- no reinterpretar el análisis
- no rehacer la frase principal
- no rehacer el cuerpo
- no añadir bloques nuevos no presentes en los ficheros generados
- no modificar el contenido salvo ajustes estrictamente técnicos de formato si el sistema de merge lo exige
- si `"$MERGE_TITLE_FILE"` no existe o está vacío, abortar
- `"$MERGE_FILE"` puede estar vacío
- si `"$PR_LINK_FILE"` no existe o está vacío, abortar
- `"$MERGE_MESSAGE_FILE"` debe generarse antes de preparar el comando final
- no ejecutar todavía ningún comando de merge real
- este paso solo debe preparar una previsualización

Abortar si:

- `"$MERGE_TITLE_FILE"` no existe
- `"$MERGE_TITLE_FILE"` está vacío
- `"$MERGE_FILE"` no existe
- `"$PR_LINK_FILE"` no existe
- `"$PR_LINK_FILE"` está vacío
- no puede obtenerse una frase principal válida desde `"$MERGE_TITLE_FILE"`
- no puede obtenerse un enlace válido de Pull Request desde `"$PR_LINK_FILE"`
- no puede generarse `"$MERGE_MESSAGE_FILE"`

Salida requerida:

- mostrar la frase principal prevista del merge
- mostrar el cuerpo previsto del merge, si existe
- mostrar el fichero final que se usaría como mensaje de merge: `"$MERGE_MESSAGE_FILE"`
- mostrar el enlace del Pull Request a cerrar
- indicar explícitamente que no se ha ejecutado ningún comando

---

### 9.3 Ejecutar merge del Pull Request

Objetivo:

Preparar y, tras autorización explícita del usuario, ejecutar el merge del Pull Request aprobado hacia `develop` usando exclusivamente el contenido de `"$MERGE_MESSAGE_FILE"` y `"$PR_LINK_FILE"`.

Definir:

- pull request: contenido de `"$PR_LINK_FILE"`
- rama destino: `develop`
- mensaje de merge: contenido de `"$MERGE_MESSAGE_FILE"`
- `MERGE_RESULT_FILE="$OUTPUT_DIR/MERGE_RESULT.txt"`

Reglas:

- no mergear directamente la rama sin Pull Request
- no cambiar la rama destino
- usar exclusivamente el Pull Request definido en `"$PR_LINK_FILE"`
- usar exclusivamente el mensaje definido en `"$MERGE_MESSAGE_FILE"`
- no inventar texto adicional para el merge
- no ejecutar el merge si el Pull Request no está aprobado o no cumple las condiciones del flujo
- no ejecutar todavía el comando real de merge hasta obtener autorización explícita del usuario
- este paso solo debe mostrar la previsualización del comando exacto que se ejecutaría
- antes de ejecutar cualquier comando, preguntar al usuario
- solo está permitido ejecutar el comando exacto previamente mostrado en la previsualización y autorizado explícitamente por el usuario
- no está permitido ejecutar comandos alternativos, equivalentes, corregidos, abreviados o reconstruidos
- no está permitido encadenar comandos
- no está permitido ejecutar comandos auxiliares antes o después del comando aprobado
- no está permitido modificar argumentos, enlace, modo de merge o `body-file` sin nueva autorización explícita del usuario
- la ejecución debe ser siempre de un único comando por vez
- el modo permitido para este flujo será `--merge`, salvo que el usuario autorice explícitamente otro
- si el comando falla, detener inmediatamente el flujo
- si el comando falla, no ejecutar ningún otro comando posterior
- si el comando falla, no reintentar
- si el comando falla, no corregir automáticamente el comando
- si el comando falla, mostrar el error recibido y esperar nuevas instrucciones del usuario
- tras ejecutar el comando autorizado, el resultado debe indicar que el merge del Pull Request se ha realizado correctamente
- el resultado debe guardarse obligatoriamente en `"$MERGE_RESULT_FILE"`
- no está permitido continuar el flujo si no existe un resultado válido y guardado del merge

Abortar si:

- el Pull Request no existe o no puede identificarse desde `"$PR_LINK_FILE"`
- no puede obtenerse un mensaje válido desde `"$MERGE_MESSAGE_FILE"`
- no puede construirse una previsualización válida del merge
- se intenta ejecutar un comando sin haber preguntado antes al usuario
- se intenta ejecutar un comando diferente al previamente autorizado
- se intenta ejecutar más de un comando
- el comando no devuelve un resultado válido de merge
- no puede guardarse `"$MERGE_RESULT_FILE"`
- `"$MERGE_RESULT_FILE"` queda vacío

Salida requerida:

- mostrar la operación prevista: merge del Pull Request de fase 1 hacia `develop`
- mostrar la frase principal y el cuerpo que alimentarían `"$MERGE_MESSAGE_FILE"`
- mostrar el enlace del Pull Request que se cerraría
- mostrar el comando exacto que se ejecutaría para realizar el merge
- indicar explícitamente que no se ejecutará ningún otro comando adicional
- indicar explícitamente que no se ha ejecutado ningún comando
- avisar de que, si el comando falla o no devuelve un resultado válido, el flujo se detendrá inmediatamente
- preguntar al usuario antes de ejecutar el merge real
- tras ejecución autorizada y exitosa, mostrar el resultado del merge
- mostrar la ruta de `"$MERGE_RESULT_FILE"`
- indicar explícitamente que el resultado ha sido validado y guardado
- esperar autorización explícita del usuario para cualquier paso posterior

Ejemplo conceptual de comando permitido:

`gh pr merge <pull-request-url> --merge --body-file "<ruta de MERGE_MESSAGE.txt>"`

Reglas sobre el ejemplo:

- si este es el comando aprobado por el usuario, solo puede ejecutarse exactamente este
- si falla, detener el flujo inmediatamente
- no ejecutar después comandos como `gh pr view`, `gh pr edit`, `git status`, `git push` o similares salvo nueva autorización explícita

---

### 9.4 Resultado de cierre del Pull Request

Mostrar:

- rama origen
- rama destino
- fichero usado para la frase principal del merge
- fichero usado para el cuerpo del merge
- fichero final usado como mensaje de merge: `"$MERGE_MESSAGE_FILE"`
- fichero usado para el enlace del Pull Request
- fichero donde se ha guardado el resultado del merge: `"$MERGE_RESULT_FILE"`
- resultado del merge ejecutado
- confirmación de que no se ha ejecutado ningún comando sin autorización explícita
- resumen del comando ejecutado para el merge del Pull Request

Abortar si:

- no existe `"$MERGE_RESULT_FILE"`
- `"$MERGE_RESULT_FILE"` está vacío
- el resultado guardado no permite confirmar que el Pull Request fue mergeado correctamente

Esperar confirmación explícita del usuario antes de continuar con cualquier paso posterior.
