# main -> Git tag -> GitHub Release

## Tag y publicación

Objetivo:

Crear el tag oficial de la versión publicada en `main` y publicar la release en GitHub adjuntando el archivo `.vsix`.

Este workflow debe ejecutarse inmediatamente después del merge `release/x.y.x -> main` y antes de la sincronización `main -> develop`.

Convención obligatoria para este caso:

- Tag: `v<RELEASE_VERSION>`
- Release title: `v<RELEASE_VERSION>`
- Target de la release: `main`
- Asset obligatorio: `VSIX_FILE`
- Notas de release: `RELEASE_NOTES.md`

Fuentes permitidas:

- `"$VAR_S1_FILE"`
- `"$PR_LINK_FILE"`
- `RELEASE_NOTES.md`
- el archivo indicado por `VSIX_FILE`

Está permitido y autorizado actualizar `"$VAR_S1_FILE"` para persistir:

- `RELEASE_TAG`
- `RELEASE_LINK_FILE`

---

## 66a.1 Variables requeridas

Leer obligatoriamente desde `"$VAR_S1_FILE"`:

- `REPOWN`
- `OUTPUT_DIR`
- `RELEASE_VERSION`
- `VSIX_FILE`
- `PR_LINK_FILE`

Si existen, también puede reutilizar:

- `RELEASE_TAG`
- `RELEASE_LINK_FILE`

Validar:

- `REPOWN` existe y no está vacía
- `OUTPUT_DIR` existe y no está vacía
- `RELEASE_VERSION` existe y no está vacía
- `VSIX_FILE` existe y apunta a un fichero `.vsix` real
- `PR_LINK_FILE` existe y contiene una URL válida de Pull Request
- `RELEASE_NOTES.md` existe en la raíz del proyecto

Si `RELEASE_TAG` no existe, definirlo exactamente como:

```text
v<RELEASE_VERSION>
```

Si `RELEASE_LINK_FILE` no existe, definirlo exactamente como:

```text
$OUTPUT_DIR/RELEASE_LINK.txt
```

Persistir ambos valores en `"$VAR_S1_FILE"` antes de continuar.

---

## 66a.2 Regla obligatoria del tag

El tag debe cumplir exactamente:

```text
v<RELEASE_VERSION>
```

Ejemplo:

```text
v1.3.49
```

Reglas:

- no crear tags con prefijos distintos
- no crear tags sin la `v`
- no reutilizar un tag ya existente
- el tag debe apuntar al estado publicado de `main`

Abortar si:

- el tag ya existe local o remotamente
- `RELEASE_VERSION` no puede mapearse de forma exacta a `v<RELEASE_VERSION>`

---

## 66a.3 Comandos previstos

Definir:

```bash
RELEASE_TAG="v$RELEASE_VERSION"
RELEASE_LINK_FILE="${RELEASE_LINK_FILE:-$OUTPUT_DIR/RELEASE_LINK.txt}"
PR_URL="$(cat "$PR_LINK_FILE")"
```

Comandos permitidos, en este orden:

### A. Sincronizar referencias remotas

```bash
git fetch origin main --tags
```

### B. Crear tag anotado sobre `origin/main`

```bash
git tag -a "$RELEASE_TAG" origin/main -m "Release $RELEASE_TAG"
```

### C. Publicar tag en remoto

```bash
git push origin "$RELEASE_TAG"
```

### D. Crear la GitHub Release con el VSIX adjunto

```bash
gh release create "$RELEASE_TAG" "$VSIX_FILE" --repo "$REPOWN" --target main --title "$RELEASE_TAG" --notes-file RELEASE_NOTES.md
```

### E. Guardar la URL de la release creada

```bash
gh release view "$RELEASE_TAG" --repo "$REPOWN" --json url --jq .url > "$RELEASE_LINK_FILE"
```

Reglas obligatorias:

- mostrar previsualización completa de los comandos antes de ejecutarlos
- pedir autorización explícita antes de la ejecución
- ejecutar exactamente esos comandos y en ese orden
- detener el flujo inmediatamente si cualquiera falla
- no sustituir `RELEASE_NOTES.md` por otro archivo
- no omitir el asset `.vsix`
- no publicar como draft salvo instrucción explícita del usuario
- no publicar como prerelease salvo instrucción explícita del usuario

---

## 66a.4 Resultado esperado

Mostrar:

- versión publicada: `RELEASE_VERSION`
- tag creado: `RELEASE_TAG`
- Pull Request origen: contenido de `"$PR_LINK_FILE"`
- asset publicado: `VSIX_FILE`
- release creada: contenido de `"$RELEASE_LINK_FILE"`

Preguntar al usuario si desea continuar con el flujo de sincronización `main -> develop` mediante `67.md`.
